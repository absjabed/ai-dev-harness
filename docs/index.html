AI Dev Harness

A development workflow for Claude Code. Copy it into a repo and answer one setup interview. From then on, specialist agents build each feature through the same approval steps, standards and safety checks.

What it is

AI Dev Harness is a development-workflow layer. It runs inside an agent harness (Claude Code) and is not an agent runtime itself. In place of ad-hoc prompting, you get specs written before code, a person approving each gate, and automated checks that run whether or not the model cooperates. It ships as a template: every project-specific value is a {{TOKEN}} or a [FILL IN] block until you configure it.

16 agent personas

BA, architect, designer, developer, QA, reviewer, security, DevOps, PM, release, orchestrator, critic and more.

27 slash commands

Studios, specialists, workflows, utilities and harness maintenance.

9 automated hooks

Block force pushes, protected-branch pushes and any request to a production host; type-check and lint after edits; warn on sensitive files.

Resumable workflows

STATE.md records phase, tasks and decisions, so a fresh session picks up exactly where the last one stopped.

Why use it

AI can already write the code. Left unsupervised, it does badly at the work around the code: following this project's conventions, proving the change works, and stopping before something irreversible. Each row below pairs one of those failures with the part of the harness that handles it.

Without a harnessWhat the harness does
You re-explain the stack, conventions and domain every session, and the answers driftThe filled .ai/config/ and .ai/context/ load automatically, scoped to the task. The project's rules live in files you can read and review
Output quality depends on how well you phrased today's promptPersonas and playbooks fix the method. /agents:review applies the same severity vocabulary on a Friday as on a Monday
AI-written code lands with a glance, because reviewing it is slower than accepting itA reviewer and a security scanner run in parallel, in separate contexts, and report findings without changing code. CRITICAL findings block the commit, and nobody has to remember to run the check
The code passed review and tests, but nobody called the API or clicked through the screenAfter review and the security scan, runtime verification makes real API calls, runs the user journeys in a browser and checks the database read-only, all against the test environment. A failed or skipped check blocks the commit until you accept it
"Tests pass", but nobody checks whether that part of the code has tests at allVerification depends on the scope: real tests where a test runner exists, otherwise a clean build plus a documented manual reproduction. The report says which one happened
One bad command (a force push, a hard reset, a deploy to production) undoes a day's workHooks block these commands at the tool call, whatever the model intended
Why a decision was made lives in a Slack thread that's now goneAppend-only decisions, learnings and design-taste logs. The designer reads the rejected patterns before proposing anything, so a rejected idea doesn't come back
A long session loses the thread, and the next one starts coldSTATE.md records the phase, tasks and decisions. Re-running the workflow resumes from there and checks that each finished phase's output still exists
Parallel work on one feature collides in the working treeThe epic path gives each sub-feature its own git worktree, merged in dependency order
Every repo grows its own private way of working with AIEvery project uses the same commands and approval steps, so someone joining a team learns them once

What it costs

Process overhead. The full path (/ba → /qa → /workflows:feature, with five STOP gates) is built for work that deserves a spec. For a typo or a one-line fix it isn't worth it, so use /agents:dev or /workflows:bugfix instead. The harness also can't make a codebase testable, and it won't catch a bad decision you approve at a gate. It prevents mistakes of forgetting; mistakes of judgment are still yours to catch.

Setup in 4 steps

  1. Copy the harness in

    From a clone of the template repo, copy into your project root:

    .ai/  .claude/  .mcp.json  CLAUDE.md  AGENTS.md  COMMANDS.md  README.md

    Optionally bring examples/fleetkeep/ for reference while configuring. .claude/HARNESS_VERSION travels with .claude/ and records which template release you copied (it matches a v<version> tag); leave it unchanged, so git log v<version>.. in the template repo later shows what you don't have yet.

    Don't copy the template's .gitignore. Your project's own .gitignore should ignore .worktrees/, .ai/features/**/e2e-screenshots/ (runtime-check screenshots can show personal data) and the per-developer .claude/settings.local.json. Keep .ai/features/ tracked, because the epic path commits planning artifacts for the worktrees to read. Keep .claude/agent-memory/ tracked too, so what the sub-agents learn is shared with the team.

  2. Run /init-project

    It interviews you across identity, repo topology, stack, commands, conventions, version control, security, design system, risk profile, branding, test environments and release deliverables. Then it fills every skeleton and writes .claude/hooks/hooks.env.

    Shape the tree while you're there: single-project repos delete the backend/ and frontend/ subfolders; headless projects delete the design subtree; unused per-stack reference folders can go.

  3. Verify nothing is unfilled

    grep -rnE '\{\{[A-Z][A-Z0-9_]*\}\}' .ai .claude CLAUDE.md | grep -vE 'CUSTOMIZATION.md|agents/harness-|workflows/harness-improvement|commands/init-project.md|standards/project/[a-z]+/(dotnet|node|react|angular)/|standards/universal/vcs/|examples/'

    Empty output means you're done. It scans .claude/ as well as .ai/, because commands and sub-agents carry tokens too, and an unfilled one there goes unnoticed until a command misbehaves.

  4. Switch the guardrails on

    hooks.env is inert until you fill it: a blank value or *_CHECK="off" skips that check silently. A file you haven't customised blocks nothing, even though the hooks look installed.

    KeyIf left unset
    PROTECTED_BRANCHESDirect pushes to main/develop aren't blocked
    TYPECHECK_CMD / LINT_CMD + PACKAGE_DIRSNo checks run after edits
    MIGRATIONS_GLOBGenerated migrations can be hand-edited silently
    SENSITIVE_CONFIG_GLOBSNo warning before editing secrets-bearing config
    TENANT_ISOLATION_CHECK + TENANT_KEYNo tenant-scoping check on data access

    Smoke-test it: on a protected branch, ask Claude to git push --force and confirm it refuses.

Sub-agents

Commands spawn these automatically, each with its own context window and a limited set of tools. The reviewer and critic get no Write or Edit tool and are told never to change code, so a review doesn't quietly turn into a fix. The limit is not a sandbox, though: both keep Bash (the reviewer saves its report through it), and memory: project lets a sub-agent write to its own memory folder.

Sub-agentToolsModelMemorySpawned by

memory: project gives that sub-agent a persistent .claude/agent-memory/<agent>/ folder: a MEMORY.md index plus topic files it writes as it learns, such as recurring defects, easy-to-miss files and project quirks. The first 200 lines (25 KB) of the index load into its prompt on every run. Project memory is meant to be committed, so every developer's runs benefit from it; review changes to it like any other diff. For per-developer memory, set memory: local (stored in .claude/agent-memory-local/ and kept out of git). Sub-agent memory is off when auto memory is disabled.

HookEventWhat it does
e2e-guard.shPreToolUse (Bash, browser MCP tools)Blocks HTTP requests, and Claude in Chrome or Playwright navigation, to any host in E2E_FORBIDDEN_HOSTS, so runtime checks never reach production

All hook behaviour comes from .claude/hooks/hooks.env, which has 26 keys. They cover version control, the deploy guard, repo layout, quality commands, sensitive files, tenant isolation, frontend env, design tokens, the TDD nudge and the runtime-verification guard. Warnings go to stderr and don't block anything. Only the git guard, the e2e guard and the sensitive-file rules block.

Path-scoped rules

Claude Code loads every .md file under .claude/rules/. A rule with paths: frontmatter loads only when Claude reads or edits a matching file, so knowledge about one area of the code uses no context elsewhere. A rule without paths: loads in every session. The template ships one example, _example-area.md, that never loads: copy it, point paths: at real code and replace the text. /utils:learn offers to save a lesson this way when it applies to one area only.

Workflows

The playbooks in .ai/workflows/ are the method the commands follow, so editing a playbook changes how the matching command behaves. They cover feature development, bug fixing, hotfixes, runtime verification, releases, code review, story generation, and harness improvement.

Runtime verification

After review and the security scan, the feature, bugfix and hotfix workflows test the change against a running system. The agent proposes the checks the change needs: API calls with curl, a run of the user journeys in a real browser (Claude in Chrome by default, with Playwright as the fallback), and read-only database checks through a database MCP server. It asks you once to confirm the plan, runs the checks against the test environment, and writes test-specs/e2e-report.md. A FAIL, or a planned check that didn't run, blocks the commit unless you explicitly accept it. Hotfixes run a single smoke check, and /workflows:verify runs the same process for ad-hoc work. e2e-guard.sh blocks any production host listed in E2E_FORBIDDEN_HOSTS.

LevelProposed when the change touchesWhat runs
APIEndpoints, request and response contracts, validation, auth or tenancycurl against the test base URL: the happy path, 400, 401, 403, 404 and 409, plus a request for another tenant's record, which must be refused
UIPages, components, forms, routing or client stateThe journeys from test-specs.md, run in Claude in Chrome (default) or Playwright, with screenshots, console errors and failed network calls recorded
DBSchema, migrations, data access or backfillsSELECT-only checks through a read-only database MCP server: the expected rows were written with the tenant key set, and nothing else changed

Safety rules. Runtime verification runs in your own session rather than in a sub-agent, so you confirm the plan, do any login yourself and decide what happens on a failure. Claude in Chrome uses your real browser profile, so before a UI journey the agent checks that the signed-in account is one of the listed test accounts. API tokens come from a token command run inline in each request, or from an environment variable exported before starting Claude Code. The agent never prints or stores them, and never writes to the database. Screenshots stay local (ignore .ai/features/**/e2e-screenshots/), and the report is checked for secrets and personal data at the commit STOP. Checking production after a deploy is left to a person or to CI.

To set it up, fill Test environments in project-config.md (URLs, start commands, where the test token comes from, test accounts and an optional read-only DB server) and set E2E_FORBIDDEN_HOSTS. Claude in Chrome needs claude --chrome (or /chrome → Enabled by default), the browser extension and a /login sign-in. A project file can't turn it on, and it doesn't work in WSL.

The epic path

When /ba produced an epic-breakdown.md, the feature workflow switches to six phases:

A validate→B design gate→C epic branch→D parallel build→E sequential merge→F review + PR

Phase D builds each sub-feature in its own git worktree under .worktrees/, so the delegated agents never share a working tree. A worktree only sees committed files, which is why the planning artifacts are committed to the epic branch first.

Release flow

Each change records what it needs at deploy time while the work is fresh, so nobody has to piece it together from git log later:

/ba: fix version→feature / bugfix / hotfix: deploy-notes.md→/workflows:release

/ba records each spec's fix version, taken from the tracker or asked for, and never guessed. The feature, bugfix and hotfix workflows write .ai/features/<slug>/deploy-notes.md, which lists settings, migrations, manual steps, checks to run after the deploy and how to roll back, or says plainly that there is no deploy impact. /workflows:release picks the notes for its version by fix version and uses them in its internal artifacts. If the deployment guide is switched on in project-config.md, it also assembles docs/release/<version>/deployment-guide-<version>.md after the confirmation gate, with an optional Word copy from .claude/scripts/md-to-docx.py. An existing guide is merged into, never overwritten.

Scope model

Every command that loads project context works out a scope first. A scope forced in .ai/config/current-scope.md wins. Otherwise the command infers backend, frontend or fullstack from your request, using the stack signals filled in at setup, and loads only that scope's config, context and standards. Force it with /utils:scope backend; release it with /utils:scope auto.

Other AI agents

The harness has two parts: the method, which works with other agents, and the enforcement, which doesn't. .ai/ is 87 files of plain markdown with no tool-specific syntax. The Claude Code coupling sits in the 27 commands (77 @file includes, 121 $ARGUMENTS refs), the 8 sub-agents, and the 9 hooks wired to Claude Code's event names.

StepWhat it gives youCost
AGENTS.md doneThe whole method as written instructions: which files to read, how to pick a scope, which playbook to follow, where to stop and ask (a review before any commit, then the five feature-path gates) and which guardrails to enforce. Works with Codex, Cursor, Gemini and CopilotNothing ongoing. It points to CLAUDE.md and .ai/ for the details, so it can't get out of date
Git hooks + CIGuardrails that hold whoever makes the edit, agent or person. Recipes for pre-push and pre-commit hooks that read the same hooks.envAbout half a day. CI is what really enforces them, because --no-verify skips local hooks
Command generatorsSlash-command convenience inside one specific non-Claude toolThe highest. The generated files go stale with every harness change unless CI fails the build when they do

What doesn't port: blocking a command at the tool call, sub-agents spawned without edit tools, and reviews running in parallel in separate contexts. On other agents these become written instructions, which the agent may or may not follow.

The recipes and the support matrix are in docs/portability.md.
